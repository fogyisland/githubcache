# M13 — Full-site i18n (zh + en) — Design Spec

## Goal

Ship a complete bilingual layer (zh-CN default + en) covering every user-facing page, both public and admin. Every label, button, heading, column header, empty state, status bar text, sidebar link, and section title must be localisable — no hardcoded English strings remain in components.

The implementation uses **next-intl** for the standard Next.js 14 App Router pattern. Server components resolve messages via `getTranslations()`; client components use `useTranslations()` from `NextIntlClientProvider`.

## Why now

The codebase has been shipping English-only UI through M0–M12. The user (zh-first) wants both languages available. The three-theme system (terminal / editorial / brutalist) and three-admin-variant system (mission_control / inspector / workbench) already established the pattern of "one piece of UI, multiple visual / linguistic variants, one switcher in chrome". Adding a language dimension follows the same shape.

## What ships

### Locale configuration

- **Locales**: `['zh', 'en']`
- **Default**: `zh` (matches the user's working language)
- **Cookie**: `ghc_lang` (1 year, SameSite=Lax, Path=/). Mirror of `ghc_theme` / `ghc_admin_variant`.
- **DB column**: `users.lang` (Prisma migration `m13_user_lang`)
- **Detection order**: cookie > DB (if authenticated) > `Accept-Language` header > `zh`
- **No URL prefix** — locale is a runtime concern, not a routing concern. Admin URLs (`/admin/...`), docs (`/docs/...`), repo detail (`/repo/...`) are not duplicated per locale.

### Switcher UX

- **`<LangSwitcher>`** in `SiteHeader` (right side, before theme switcher) and in `AdminShell` utility bar.
- Two-button toggle: `中` / `EN`, with `aria-pressed`.
- Server action `setLangAction(locale)` validates against `LOCALES`, sets cookie, persists to `users.lang` if logged in, calls `revalidatePath('/', 'layout')`.

### Message dictionaries

Two files at `messages/{zh,en}.json`. Namespaces:

| Namespace | Used by |
|---|---|
| `common` | Save / Cancel / Delete / Edit / Search / Loading / Error / Back / Yes / No |
| `nav` | Home / Status / Admin / Docs / Login / Logout |
| `theme` | Theme switcher labels (T/E/B) + "Switch to X theme" aria |
| `lang` | Lang switcher labels (中/EN) |
| `public.home` | Hero, tagline, lookup form, recent lookups, stats, features, how-it-works, footer |
| `public.repo` | Repo detail page: loading, not-found, error, all metadata labels |
| `login` | Title, tagline, email/password labels, submit, error states |
| `docs.shell` | Docs sidebar labels |
| `docs.api` | Endpoint page sections: curl, request, response, headers, errors, "Example response", "Response headers" |
| `admin.shell` | Sidebar 7-section labels, dashboard, palette, status bar |
| `admin.users` | List + detail pages |
| `admin.apiKeys` | List + detail pages |
| `admin.githubTokens` | List + detail pages |
| `admin.reports` | Charts labels, filter controls |
| `admin.audit` | Audit search log, action labels |
| `admin.refresh` | Manual refresh, queue pause labels |

### Pages translated

- `src/app/page.tsx` + `_components/*`
- `src/app/repo/[owner]/[name]/page.tsx` + `_components/*`
- `src/app/login/page.tsx` + `_login-form.tsx`
- `src/app/admin/layout.tsx` + `page.tsx` + `users/...` + `api-keys/...` + `github-tokens/...` + `reports/...` + `audit/...` + `refresh/...`
- `src/app/admin/_components/{admin-shell,admin-sidebar,command-palette,admin-status-bar,admin-page-header,...}.tsx`
- `src/app/_components/{site-header,site-footer,theme-switcher}.tsx`
- `src/app/docs/layout.tsx` + `page.tsx` + `api/{v1-status,v1-repos,query}/page.tsx`

### What does NOT ship

- **API contract** — JSON field names, route paths, error codes remain English.
- **Repo data** — repo names, descriptions, topics (real GitHub content) remain in their original language.
- **Audit log content** — `audit_log.details` JSON remains English (it's structured data, not UI copy).
- **M12 docs API examples** — curl commands, JSON field names stay English.
- **Code identifiers** — class names, log messages, error codes — internal, not user-facing.
- **URL prefixes** — no `/zh/...` or `/en/...`. The cookie + DB resolve locale at request time.

## Architecture

### File layout (new)

```
src/i18n/
  config.ts         # LOCALES, defaultLocale, localePrefix strategy
  routing.ts        # locale detection: cookie + DB + Accept-Language
  request.ts        # getRequestConfig for next-intl (server-only)
src/lib/lang/
  cookie.ts        # read/write ghc_lang cookie (mirror theme/cookie.ts)
  registry.ts       # locale registry + isLocale + resolveLocale
src/app/_actions/
  set-lang.ts       # setLangAction (server action)
messages/
  zh.json           # Chinese messages
  en.json           # English messages
src/components/lang-switcher/
  lang-switcher.tsx       # client component
  lang-switcher.module.css  # if needed
prisma/
  schema.prisma         # + lang String @default("zh") @Users
  migrations/m13_user_lang/
```

### Server component pattern

```tsx
// In every server component
import { getTranslations } from 'next-intl/server';

export default async function Page() {
  const t = await getTranslations('public.home');
  return <h1>{t('hero.title')}</h1>;
}
```

### Client component pattern

```tsx
'use client';
import { useTranslations } from 'next-intl';

export function Component() {
  const t = useTranslations('admin.users');
  return <button>{t('actions.save')}</button>;
}
```

### Root layout integration

```tsx
// src/app/layout.tsx
import { NextIntlClientProvider } from 'next-intl';
import { getLocale, getMessages } from 'next-intl/server';

export default async function RootLayout({ children }) {
  const locale = await getLocale();
  const messages = await getMessages();
  return (
    <html lang={locale}>
      <body>
        <NextIntlClientProvider locale={locale} messages={messages}>
          {children}
        </NextIntlClientProvider>
      </body>
    </html>
  );
}
```

### Persistence on login

When `POST /api/admin/auth/login` succeeds, update `users.lang` to the current locale (server reads cookie). On any `setLangAction`, if logged in, write to `users.lang`. On logout, do NOT clear `users.lang` — language preference is independent of session.

## Risks

| Risk | Mitigation |
|---|---|
| Message-key drift between zh and en files | Unit test asserts every key in zh.json exists in en.json and vice versa. |
| Some components use string concatenation that breaks locale-aware formatting | Use ICU MessageFormat `{count, plural, one {# repo} other {# repos}}`. |
| Server-action locale coercion (cookie can be tampered) | `setLangAction` validates input via zod with `z.enum(LOCALES)`. |
| Mixed content during HMR | Restart dev server after config changes. CI must rebuild. |
| Some text is hardcoded inside CSS (e.g., `content: "→"`) | Keep symbolic glyphs as-is; only translate user-visible copy. |
| Repo metadata labels use shared component reused across detail page | The component receives `t` via prop from parent. |

## Out of scope

- RTL / more locales (Arabic, Japanese)
- Locale-prefixed URLs (`/en/admin/...`)
- Translated audit log content / API errors / DB-stored data
- AI-translated docs examples (English only — they're API contracts)
